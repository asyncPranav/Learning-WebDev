# Restrict updation of few fields by user on /patch route (API level validations)


- Old code : 
```js
// Update /user/:userId - update a user by userId
app.patch("/user/:userId", async (req, res) => {
  try {
    const user = await User.findByIdAndUpdate(req.params.userId, req.body, {
      runValidators: true,
    });
    if (!user) {
      return res.status(404).json({
        success: false,
        message: "User not found",
      });
    }
    return res.status(200).json({
      success: true,
      message: "User updated successfully",
      user,
    });
  } catch (error) {
    return res.status(500).json({
      success: false,
      message: "Error updating user",
      error: error.message,
    });
  }
});
```
---

Yes. For DevTinder, you should **never directly pass `req.body` into `findByIdAndUpdate()`**, because then a user can send any field—including `email`, `password`, etc.

Your requirement is:

### 🔒 Cannot update

* username
* name
* email
* password
* gender

### ✅ Can update

* age
* about
* skills
* photoUrl

The best approach is to create an **allowed fields list**.

## Recommended implementation

```js
// Update /user/:userId - update a user by userId
app.patch("/user/:userId", async (req, res) => {
  try {
    // Fields that users are allowed to update
    const allowedUpdates = ["age", "about", "skills", "photoUrl"];

    // Get all fields sent by the user
    const requestedUpdates = Object.keys(req.body);

    // Check whether every requested field is allowed
    const isValidUpdate = requestedUpdates.every((field) =>
      allowedUpdates.includes(field),
    );

    // If user tries to update a restricted field
    if (!isValidUpdate) {
      return res.status(400).json({
        success: false,
        message: "You can only update age, about, skills, and photoUrl",
      });
    }

    const user = await User.findByIdAndUpdate(
      req.params.userId,
      req.body,
      {
        new: true,
        runValidators: true,
      },
    );

    if (!user) {
      return res.status(404).json({
        success: false,
        message: "User not found",
      });
    }

    return res.status(200).json({
      success: true,
      message: "User updated successfully",
      user,
    });
  } catch (error) {
    return res.status(500).json({
      success: false,
      message: "Error updating user",
      error: error.message,
    });
  }
});
```

# How it works

Suppose the user sends:

```json
{
  "age": 22,
  "about": "I am a Node.js developer",
  "skills": ["JavaScript", "Node.js"]
}
```

Then:

```js
Object.keys(req.body)
```

becomes:

```js
["age", "about", "skills"]
```

We check every field against:

```js
const allowedUpdates = ["age", "about", "skills", "photoUrl"];
```

Since all fields are allowed → update proceeds.

---

## ❌ If someone sends this

```json
{
  "name": "Hacker",
  "email": "hacker@gmail.com"
}
```

Then:

```js
requestedUpdates = ["name", "email"];
```

Neither is allowed, so:

```js
isValidUpdate === false
```

And the request returns:

```json
{
  "success": false,
  "message": "You can only update age, about, skills, and photoUrl"
}
```

# Important improvement: `new: true`

In your original code:

```js
const user = await User.findByIdAndUpdate(...)
```

By default, Mongoose returns the **old user document**.

So add:

```js
new: true
```

```js
{
  new: true,
  runValidators: true
}
```

Now the response contains the **updated user**.

# 📌 DevTinder Notes — PATCH and Allowed Updates

### `PATCH`

Used to partially update a resource.

Example:

```http
PATCH /user/123
```

### Problem with directly using `req.body`

```js
User.findByIdAndUpdate(userId, req.body);
```

This is dangerous because the client can update fields you did not intend to allow.

### Solution: Allowlist

```js
const allowedUpdates = ["age", "about", "skills", "photoUrl"];
```

Only fields in this list can be updated.

### Validation

```js
const requestedUpdates = Object.keys(req.body);

const isValidUpdate = requestedUpdates.every((field) =>
  allowedUpdates.includes(field)
);
```

This ensures **every field sent by the client is allowed**.

---

One thing I'll point out for our DevTinder project: eventually, when we add authentication, you generally **should not use `:userId` for a normal user's profile edit**. The logged-in user should update their own profile through something like:

```http
PATCH /profile/edit
```

Then the backend gets the user's identity from authentication/session data. Otherwise, a user could potentially try changing another user's ID in the URL.

For now, though, your current route is perfect for understanding the update logic.

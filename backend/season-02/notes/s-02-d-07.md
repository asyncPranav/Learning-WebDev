# MongoDB / Mongoose Imp Points

### 1. Fields Not Defined in the Schema

By default, **Mongoose ignores fields that are not defined in the schema** when creating or updating a document.

For example, if the schema is:

```js
const userSchema = new mongoose.Schema({
  name: String,
  email: String,
});
```

and the request body contains:

```js
{
  name: "Rahul",
  email: "rahul@example.com",
  age: 25
}
```

Since `age` is not defined in the schema, Mongoose will **not save it** by default.

> **Note:** This behavior depends on the schema's `strict` option. The default is `strict: true`.

---

### 2. `findById()` Internally Uses an ID Query

Mongoose's:

```js
User.findById(userId)
```

is essentially shorthand for:

```js
User.findOne({ _id: userId })
```

So `findById()` specifically searches using the document's **`_id`** field.

---

### 3. Query Methods Accept Options

Many Mongoose query methods accept an **options object** to customize query/update behavior.

For example:

```js
User.findByIdAndUpdate(
  userId,
  { name: "Rahul" },
  { new: true }
);
```

Here, `{ new: true }` tells Mongoose to return the **updated document**.

Without it, Mongoose returns the **document from before the update** by default.

> Options are **method-specific**. Different Mongoose methods support different options.

---

### 4. Common `findByIdAndUpdate()` Options

#### `new: true`

Return the document **after the update**.

```js
{ new: true }
```

#### `runValidators: true`

Run schema validators while updating.

```js
{ new: true, runValidators: true }
```

#### `upsert: true`

If the document exists → update it.
If it doesn't exist → create it.

```js
{ upsert: true }
```

> **Upsert = Update + Insert**

---

### 5. JavaScript Object vs JSON

**JavaScript object** is a data structure inside JavaScript:

```js
const user = {
  name: "Rahul",
  age: 25
};
```

**JSON** is a **string/text format** used to transfer data.

```json
{
  "name": "Rahul",
  "age": 25
}
```

Key difference:

```text
JS Object → JavaScript data structure
JSON      → String/text data format
```

In an Express API:

```js
app.use(express.json());
```

converts incoming JSON request data into a **JavaScript object** available through:

```js
req.body
```

### 6. `PUT` vs `PATCH`

Both are used to update resources, but their intended behavior is different.

#### `PUT` → Replace the Resource

`PUT` is generally used to **replace the entire resource**.

Suppose the schema has 4 fields:

```js
{
  name,
  email,
  age,
  gender
}
```

If the existing user is:

```js
{
  name: "Rahul",
  email: "rahul@gmail.com",
  age: 25,
  gender: "male"
}
```

and we send:

```http
PUT /user/123
```

```json
{
  "name": "Aman"
}
```

The idea of `PUT` is that we are providing the **new complete representation** of the resource.

So, fields that are not provided (`email`, `age`, `gender`) may be **replaced/removed depending on how the API implements PUT**.

> **PUT = Replace the complete resource**

---

#### `PATCH` → Partial Update

`PATCH` is specifically meant for **partial updates**.

If we send:

```http
PATCH /user/123
```

```json
{
  "name": "Aman"
}
```

Only `name` is changed.

The other fields remain unchanged:

```js
{
  name: "Aman",
  email: "rahul@gmail.com",
  age: 25,
  gender: "male"
}
```

> **PATCH = Update only the fields provided**

### Easy Way to Remember

```text
PUT    → "Here is the new complete resource"
PATCH  → "Change only these fields"
```

> **Important:** Mongoose's `findByIdAndUpdate()` performs an update operation; it does not automatically make a `PUT` request a true full-document replacement. The `PUT` vs `PATCH` semantics are primarily an **API design/convention**, so your route handler must enforce the behavior you want.
